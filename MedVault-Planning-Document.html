MedVault — Patient Medical Records Management System

Full Product & Engineering Plan (BRD, Architecture, Database, APIs, Security, Deployment)

1. Business Requirements Document (BRD)

1.1 Purpose

Build a secure web application ("MedVault") that lets patients upload, organize, and manage their personal medical documents — prescriptions, lab reports, X-ray/imaging reports, discharge summaries, vaccination records, insurance documents, etc. — in one place, and optionally share them with doctors or family members.

1.2 Goals

  • Give patients a single, secure, searchable repository for all medical documents.
  • Reduce dependency on physical paperwork and fragmented storage (WhatsApp, email, phone gallery).
  • Allow structured tagging (document type, date, doctor, hospital, tags) for fast retrieval.
  • Allow controlled, time-boxed sharing of records with third parties (doctor, family member, insurer) via secure links.
  • Be compliant with data-privacy best practices comparable to HIPAA/GDPR principles even if not formally certified initially.

1.3 Stakeholders

Stakeholder Interest
Patient (primary user) Upload, view, organize, share, delete own records
Doctor (secondary user, optional in v1) View records shared with them
Family member / Caregiver (optional) View/manage records for a dependent (e.g., child, elderly parent)
Admin User management, system monitoring, compliance audits
System Automated OCR/tagging, reminders (prescription refill, report follow-up)

1.4 Scope

In scope — MVP (Phase 1) - Patient registration/login (email + password, OTP-based email verification) - Upload documents (PDF, JPG, PNG, DOCX up to a size limit) - Categorize by type: Prescription, Lab Report, X-ray/Imaging, Discharge Summary, Vaccination, Insurance, Other - Metadata: title, doctor name, hospital/clinic, date of record, tags, notes - View, download, rename, delete, search, filter, sort records - Folder/category-based organization - Basic dashboard (recent uploads, storage used, record counts by category) - Secure file storage (MinIO, S3-compatible) with encryption at rest - Audit log of access/uploads/downloads - Responsive web UI (desktop + mobile browser)

In scope — Phase 2 - Share a record (or set of records) with a doctor/family member via expiring secure link or invited account - Multi-profile support (manage records for dependents under one account) - OCR text extraction from scanned reports + full-text search - Reminders/notifications (medicine refill, follow-up visit, report expiry) - Mobile app (React Native) reusing the same APIs

In scope — Phase 3 - Doctor-side portal (view shared records, add notes) - Integration with lab/hospital APIs (auto-import reports) — e.g. HL7/FHIR - Analytics/health trends dashboard (e.g., blood pressure/sugar trend from lab reports) - Two-factor authentication (TOTP), biometric login on mobile

Out of scope (for now) - Direct EHR/insurance claim integrations - Telemedicine / video consultation - Prescription e-ordering to pharmacy

1.5 Functional Requirements

ID Requirement
FR-1 Users can register, verify email, log in, log out, reset password
FR-2 Users can upload one or more files with metadata in a single action
FR-3 Users can view a list/grid of their records with thumbnails/previews
FR-4 Users can search records by title, tag, doctor, category, date range
FR-5 Users can download the original file or view it inline (PDF/image viewer)
FR-6 Users can edit metadata or delete a record (soft delete with recovery window)
FR-7 Users can create/manage family member profiles and switch between them
FR-8 Users can generate a shareable, expiring, revocable link for a record or record set
FR-9 System logs every access/download/share event per record (audit trail)
FR-10 System enforces per-user storage quota and shows usage
FR-11 Admin can view system health, manage users, and review flagged activity

1.6 Non-Functional Requirements

Category Requirement
Security TLS 1.2+ everywhere, encryption at rest (MinIO SSE), password hashing (bcrypt/argon2), JWT-based auth, RBAC
Privacy Data isolated per patient; no cross-tenant access; audit trail; ability to export/delete own data (GDPR "right to be forgotten")
Availability 99.5%+ target; horizontally scalable stateless backend
Performance File upload ≤ 25MB completes < 10s on broadband; list APIs < 300ms p95
Scalability Support growth from 1K → 1M users without architecture rewrite (stateless services + object storage + DB read replicas)
Usability Mobile-responsive; accessible (WCAG 2.1 AA where practical)
Compliance-readiness Architecture should not block future HIPAA/GDPR/ISO 27001 certification
Observability Centralized logs, metrics, tracing, alerting

1.7 Assumptions & Constraints

  • Initial deployment is self-hosted or on a single cloud provider (AWS/GCP/Azure/on-prem K8s).
  • MinIO is used instead of a managed cloud object store for portability and cost control, but the abstraction should allow swapping to AWS S3 later (S3-compatible API).
  • Regulatory certification (HIPAA/GDPR formal compliance) is a business/legal process on top of this technical foundation — this plan makes the architecture capable of compliance, not a legal guarantee.

1.8 Success Metrics

  • % of users who upload ≥ 1 document within first session
  • Average time-to-find-a-record (search latency + UX)
  • Monthly active users, retention at 30/90 days
  • Zero critical security incidents; audit-log coverage of 100% of record access events

Key architectural decisions

  1. Stateless Spring Boot services behind a load balancer → horizontal scaling, easy container orchestration (Docker/K8s).
  2. PostgreSQL for all relational/metadata data (users, records metadata, permissions, audit logs) — strong ACID guarantees needed for medical data.
  3. MinIO for actual file bytes (S3-compatible API) — decouples large binary storage from the DB, supports presigned URLs, versioning, and server-side encryption. Swappable for AWS S3/GCS later with near-zero code change (same S3 SDK).
  4. Redis for session/token caching, rate limiting, and short-lived share-link caching.
  5. JWT (access + refresh token) based stateless auth, with optional OAuth2 login (Google) later.
  6. Audit service writes an immutable log (append-only table, optionally also mirrored to a separate log store) for every read/write/share/download — required for medical-data trust and future compliance.
  7. API Gateway/Nginx in front of services handles TLS termination, routing, and basic rate limiting.
  8. Presigned URLs: for large-file upload/download the backend should generate MinIO presigned URLs, so files can go client ⇄ MinIO directly without proxying every byte through Spring Boot (better performance, less backend load), while Spring Boot still validates, records metadata, and controls access before generating the URL.

3. Complete Application Flow

3.1 User Registration & Login

sequenceDiagram actor U as Patient participant FE as React App participant API as Spring Boot API participant DB as PostgreSQL participant MAIL as Email Service U->>FE: Fill signup form (name, email, password) FE->>API: POST /api/v1/auth/register API->>DB: Create user (status=UNVERIFIED) API->>MAIL: Send verification OTP/link MAIL-->>U: Email with OTP U->>FE: Enter OTP FE->>API: POST /api/v1/auth/verify-email API->>DB: Update status=ACTIVE API-->>FE: Success U->>FE: Login (email/password) FE->>API: POST /api/v1/auth/login API->>DB: Validate credentials API-->>FE: access_token (JWT, 15 min) + refresh_token (7-30 days, httpOnly cookie) FE->>FE: Store access token in memory, refresh via cookie

3.2 Upload a Medical Record

sequenceDiagram actor U as Patient participant FE as React App participant API as Spring Boot API participant DB as PostgreSQL participant S3 as MinIO U->>FE: Select file(s) + fill metadata (type, date, doctor, tags) FE->>API: POST /api/v1/records/initiate-upload (filename, size, mimeType) API->>API: Validate file type/size, virus-scan hook, quota check API->>DB: Create record row (status=PENDING), generate storage key API->>S3: Request presigned PUT URL API-->>FE: presignedUrl + recordId FE->>S3: PUT file directly to MinIO (presigned URL) S3-->>FE: 200 OK FE->>API: POST /api/v1/records/{id}/complete-upload API->>S3: HEAD object (verify size/checksum) API->>DB: Update record status=ACTIVE, save checksum, size API->>DB: Insert audit_log (UPLOAD) API-->>FE: Record details (ready to view)

3.3 View / Download a Record

sequenceDiagram actor U as Patient participant FE as React App participant API as Spring Boot API participant S3 as MinIO U->>FE: Click "View/Download" on a record FE->>API: GET /api/v1/records/{id}/download-url API->>API: Check ownership/permission API->>S3: Generate presigned GET URL (short-lived, e.g. 5 min) API->>API: Write audit_log (VIEW/DOWNLOAD) API-->>FE: presignedUrl FE->>S3: GET file (direct download/preview)

3.4 Share a Record

sequenceDiagram actor U as Patient participant FE as React App participant API as Spring Boot API participant DB as PostgreSQL actor R as Recipient (doctor/family) U->>FE: Select record(s) → "Share" FE->>API: POST /api/v1/shares (recordIds, expiresAt, recipientEmail?, permission=VIEW) API->>DB: Create share row + unique token API-->>FE: Shareable link (https://app/share/{token}) U->>R: Sends link (out of band) R->>FE: Opens link FE->>API: GET /api/v1/shares/{token} API->>DB: Validate token not expired/revoked API-->>FE: Read-only record view (no account needed, or login if recipient account required)

3.5 Multi-Profile (Dependents) Flow — Phase 2

  • Primary account can create "linked profiles" (e.g., child, parent).
  • Each linked profile has its own set of records but shares the parent account's login.
  • Access is modeled via family_members + profile_id on records, with the owning user_id unchanged — see schema below.

4.2 DDL (core tables)

CREATE EXTENSION IF NOT EXISTS "pgcrypto";

CREATE TABLE users (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email             VARCHAR(255) UNIQUE NOT NULL,
    password_hash     VARCHAR(255) NOT NULL,
    full_name         VARCHAR(150) NOT NULL,
    phone             VARCHAR(20),
    role              VARCHAR(20) NOT NULL DEFAULT 'PATIENT', -- PATIENT, DOCTOR, ADMIN
    status            VARCHAR(20) NOT NULL DEFAULT 'UNVERIFIED', -- UNVERIFIED, ACTIVE, SUSPENDED, DELETED
    email_verified    BOOLEAN NOT NULL DEFAULT FALSE,
    mfa_enabled       BOOLEAN NOT NULL DEFAULT FALSE,
    mfa_secret        VARCHAR(255),
    storage_quota_mb  BIGINT NOT NULL DEFAULT 2048,
    storage_used_mb   BIGINT NOT NULL DEFAULT 0,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE profiles (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id       UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    display_name  VARCHAR(150) NOT NULL,
    relation      VARCHAR(30) NOT NULL DEFAULT 'SELF', -- SELF, CHILD, PARENT, SPOUSE, OTHER
    date_of_birth DATE,
    gender        VARCHAR(15),
    is_primary    BOOLEAN NOT NULL DEFAULT TRUE,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE categories (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name              VARCHAR(80) NOT NULL,
    code              VARCHAR(40) UNIQUE NOT NULL, -- PRESCRIPTION, LAB_REPORT, XRAY, DISCHARGE_SUMMARY, VACCINATION, INSURANCE, OTHER
    icon              VARCHAR(50),
    is_system_default BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE medical_records (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    profile_id    UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    category_id   UUID NOT NULL REFERENCES categories(id),
    title         VARCHAR(200) NOT NULL,
    description   TEXT,
    doctor_name   VARCHAR(150),
    hospital_name VARCHAR(150),
    record_date   DATE,
    status        VARCHAR(20) NOT NULL DEFAULT 'ACTIVE', -- PENDING, ACTIVE, ARCHIVED, DELETED
    visibility    VARCHAR(20) NOT NULL DEFAULT 'PRIVATE', -- PRIVATE, SHARED
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at    TIMESTAMPTZ
);
CREATE INDEX idx_records_profile ON medical_records(profile_id);
CREATE INDEX idx_records_category ON medical_records(category_id);
CREATE INDEX idx_records_date ON medical_records(record_date);
CREATE INDEX idx_records_title_trgm ON medical_records USING gin (title gin_trgm_ops);

CREATE TABLE record_files (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    record_id         UUID NOT NULL REFERENCES medical_records(id) ON DELETE CASCADE,
    storage_bucket    VARCHAR(100) NOT NULL,
    storage_key       VARCHAR(500) NOT NULL,
    original_filename VARCHAR(255) NOT NULL,
    mime_type         VARCHAR(100) NOT NULL,
    size_bytes        BIGINT NOT NULL,
    checksum_sha256   VARCHAR(64),
    upload_status     VARCHAR(20) NOT NULL DEFAULT 'PENDING', -- PENDING, UPLOADED, FAILED
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_files_record ON record_files(record_id);

CREATE TABLE tags (
    id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name    VARCHAR(60) NOT NULL,
    UNIQUE(user_id, name)
);

CREATE TABLE record_tags (
    record_id UUID NOT NULL REFERENCES medical_records(id) ON DELETE CASCADE,
    tag_id    UUID NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
    PRIMARY KEY (record_id, tag_id)
);

CREATE TABLE shares (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    record_id       UUID NOT NULL REFERENCES medical_records(id) ON DELETE CASCADE,
    created_by      UUID NOT NULL REFERENCES users(id),
    token           VARCHAR(128) UNIQUE NOT NULL,
    recipient_email VARCHAR(255),
    permission      VARCHAR(20) NOT NULL DEFAULT 'VIEW', -- VIEW, DOWNLOAD
    expires_at      TIMESTAMPTZ NOT NULL,
    revoked         BOOLEAN NOT NULL DEFAULT FALSE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_shares_token ON shares(token);

CREATE TABLE share_access_logs (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    share_id        UUID NOT NULL REFERENCES shares(id) ON DELETE CASCADE,
    accessed_by_ip  VARCHAR(64),
    user_agent      VARCHAR(255),
    accessed_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Append-only audit table; never UPDATE, only INSERT
CREATE TABLE audit_logs (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID REFERENCES users(id),
    record_id   UUID REFERENCES medical_records(id),
    action      VARCHAR(40) NOT NULL, -- LOGIN, LOGOUT, UPLOAD, VIEW, DOWNLOAD, SHARE, DELETE, UPDATE_METADATA
    ip_address  VARCHAR(64),
    user_agent  VARCHAR(255),
    metadata    JSONB,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_audit_user ON audit_logs(user_id);
CREATE INDEX idx_audit_record ON audit_logs(record_id);
CREATE INDEX idx_audit_created ON audit_logs(created_at);

CREATE TABLE refresh_tokens (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token_hash  VARCHAR(255) NOT NULL,
    expires_at  TIMESTAMPTZ NOT NULL,
    revoked     BOOLEAN NOT NULL DEFAULT FALSE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE notifications (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    type       VARCHAR(40) NOT NULL,
    title      VARCHAR(150) NOT NULL,
    body       TEXT,
    is_read    BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

Design notes - medical_records never stores the file itself — only metadata; actual bytes live in MinIO, referenced by record_files.storage_key. - Soft delete via deleted_at/status so patients can "recover" accidentally deleted records within a grace window (e.g., 30 days) before a background job purges them from MinIO too. - audit_logs is append-only and should ideally also be shipped to a separate immutable store (e.g., write-once S3/MinIO bucket or a log pipeline) for tamper resistance. - Full-text search: start with Postgres pg_trgm/tsvector on title/description; move to Elasticsearch in Phase 2 once OCR text needs indexing. - Partition audit_logs and share_access_logs by month once volume grows (Postgres native partitioning).

5. API Structure & Endpoints

Base path: /api/v1. All endpoints (except auth/share-view) require Authorization: Bearer <JWT>.

5.1 Auth

Method Endpoint Description
POST /auth/register Create account (email, password, full name)
POST /auth/verify-email Verify OTP/token sent to email
POST /auth/login Login → returns access token + sets refresh cookie
POST /auth/refresh Exchange refresh token for new access token
POST /auth/logout Revoke refresh token
POST /auth/forgot-password Send password reset link
POST /auth/reset-password Reset password using token
POST /auth/mfa/enable Enable TOTP MFA (Phase 3)
POST /auth/mfa/verify Verify TOTP code at login

5.2 Users & Profiles

Method Endpoint Description
GET /users/me Get current user profile + storage usage
PATCH /users/me Update name/phone
POST /users/me/change-password Change password
GET /profiles List family/linked profiles
POST /profiles Create a new profile (dependent)
PATCH /profiles/{id} Update profile
DELETE /profiles/{id} Delete profile (cascades records — with confirmation)

5.3 Categories & Tags

Method Endpoint Description
GET /categories List system categories
GET /tags List user's tags
POST /tags Create tag

5.4 Medical Records

Method Endpoint Description
GET /records List records (filters: profileId, categoryId, tag, doctor, dateFrom, dateTo, q; paginated)
GET /records/{id} Get record detail + file metadata
POST /records Create record metadata (before file upload)
PATCH /records/{id} Update metadata (title, tags, doctor, etc.)
DELETE /records/{id} Soft-delete record
POST /records/{id}/restore Restore soft-deleted record
GET /records/{id}/files/{fileId}/upload-url Get presigned PUT URL
POST /records/{id}/files/{fileId}/complete Confirm upload completed
GET /records/{id}/files/{fileId}/download-url Get presigned GET URL
GET /records/search Full-text search across title/description/OCR text

5.5 Sharing

Method Endpoint Description
POST /shares Create share link for one or more records
GET /shares List active shares created by user
DELETE /shares/{id} Revoke a share
GET /shares/public/{token} (No auth) Resolve a share token → record metadata + view/download URL

5.6 Notifications

Method Endpoint Description
GET /notifications List notifications
PATCH /notifications/{id}/read Mark as read

5.7 Admin (role=ADMIN)

Method Endpoint Description
GET /admin/users List/search users
PATCH /admin/users/{id}/status Suspend/reactivate user
GET /admin/audit-logs Query audit logs
GET /admin/system/health System health/metrics summary

6.3 Security filter chain (conceptual)

Request
  → CORS filter
  → JwtAuthenticationFilter (parses Bearer token, sets SecurityContext)
  → RateLimitFilter (Redis token bucket per user/IP)
  → Method-level @PreAuthorize checks (role + ownership via PermissionEvaluator)
  → Controller → Service → Repository

6.4 Ownership/authorization pattern

Every record-level endpoint checks that the authenticated user owns the profile_id tied to the record (or has an active, unexpired share), enforced centrally, e.g.:

@PreAuthorize("@recordPermissionEvaluator.canAccess(#recordId, principal)")
@GetMapping("/{recordId}")
public ApiResponse<RecordDto> getRecord(@PathVariable UUID recordId) { ... }

This avoids relying on ad-hoc if checks scattered in services and centralizes the security-critical logic.

6.5 Growth path: modular monolith → microservices

Start as a single Spring Boot deployable with clear package boundaries (as above). If/when scale demands it, auth, file, and notification packages are the natural first extraction candidates into separate services, since they have the fewest cross-cutting transactional dependencies on record/profile.

7.4 Security practices on frontend

  • Store the access token in memory only (React context/Zustand), never in localStorage, to reduce XSS token-theft risk; refresh token lives in an httpOnly, secure, SameSite=strict cookie.
  • Axios response interceptor: on 401, attempt silent /auth/refresh once, then retry original request; on repeat failure, log out.
  • Sanitize any rendered user-supplied text (React escapes by default; avoid dangerouslySetInnerHTML).
  • Enforce client-side file-type/size checks as a UX nicety — real enforcement is server-side.
  • CSP headers configured at the hosting/CDN layer (see Security section).

8. MinIO Integration Details

8.1 Bucket design

  • One bucket per environment: medvault-prod, medvault-staging.
  • Object key convention: {profileId}/{recordId}/{fileId}-{sanitizedFilename} This keeps a natural per-record grouping and avoids collisions.
  • Enable versioning on the bucket so accidental overwrite/delete is recoverable.
  • Enable server-side encryption (SSE-S3 or SSE-KMS if MinIO is configured with a KMS) so data at rest is encrypted transparently.
  • Configure lifecycle rules: permanently purge objects tied to soft-deleted records after the retention window (e.g. 30 days) via a scheduled job that calls MinIO's remove API — do NOT rely solely on MinIO lifecycle rules since deletion must be tied to the DB record's deleted_at state, not just object age.
  • Set a bucket policy so the bucket itself is private; all access happens through presigned URLs issued by the backend, never public reads.

8.2 Presigned URL flow (already shown in sequence diagrams)

  • Upload: backend calls MinioClient.getPresignedObjectUrl(PUT, bucket, key, expiry=5min) after validating file type/size/quota; frontend PUTs directly to MinIO.
  • Download/view: backend calls the same for GET, short expiry (e.g., 2–5 min), and only after verifying the requester owns/has-share-access to the record; every call is audit-logged.
  • This keeps large binary traffic off the Spring Boot instances (they only issue short-lived signed URLs), which is critical for scaling.

8.3 Virus/malware scanning

  • Before marking an upload ACTIVE, optionally route the object through a ClamAV scan (via a sidecar/service subscribed to MinIO bucket notifications, or a synchronous scan step before generating the presigned URL confirmation). Flag/quarantine infected files instead of serving them.

8.4 MinIO deployment

  • Dev: single-node MinIO via Docker Compose.
  • Prod: MinIO in distributed mode (min. 4 nodes, erasure coding) for durability, or use a managed S3-compatible service if not self-hosting. The application code should depend only on the S3 API (via the MinIO SDK, which is S3-compatible), so switching to AWS S3 later is a config change, not a rewrite.

9. Authentication & Authorization

9.1 Authentication

  • Primary: email + password (bcrypt/Argon2 hashed, never plain/reversible).
  • Tokens: JWT access token (short-lived, 15 min, signed RS256/HS256) + opaque refresh token (7–30 days, stored hashed in refresh_tokens table, rotated on each use, revocable).
  • Email verification required before first login-enabled use (OTP or link).
  • MFA (Phase 3): TOTP (Google Authenticator-compatible) as an optional, then eventually mandatory, layer — sensitive medical data justifies pushing users toward MFA.
  • OAuth2 social login (optional): Google login via Spring Security OAuth2 client, mapped to the same users table.

9.2 Authorization (RBAC + ownership)

Role Capabilities
PATIENT Full CRUD on own profiles/records; create shares
DOCTOR (Phase 3) View records explicitly shared with their account
ADMIN User management, audit log access, system monitoring — no direct access to patient files unless explicitly elevated for support with logged justification
  • Enforce row-level ownership: every record/profile query is scoped by profile.user_id = authenticatedUserId (or valid share token) — implemented via the centralized PermissionEvaluator shown earlier, not per-controller ad hoc checks.
  • Admin accounts should NOT have a blanket "view any file" capability by default — this is a deliberate privacy control; break-glass access (if ever needed) must be explicitly logged and time-boxed.

9.3 Share-link security

  • Token: cryptographically random, ≥128 bits, stored as the token itself (or its hash) with an expiry and revoked flag.
  • Rate-limit share-token resolution endpoint to prevent brute-force guessing.
  • Optional: require recipient email verification (OTP) before granting access, for stricter sharing.

14. Summary of Key Recommendations

  1. Start as a modular monolith in Spring Boot — faster to build and operate than microservices at this stage; package boundaries make future extraction easy.
  2. Keep file bytes in MinIO, metadata in Postgres, always via presigned URLs — never proxy large files through the app server.
  3. Treat this as sensitive health data from day one: append-only audit logs, strict row-level ownership checks, encryption everywhere, no implicit admin file access.
  4. Use JWT access + rotated refresh tokens, access token in memory on the frontend, refresh token in an httpOnly cookie.
  5. Design the storage abstraction against the S3 API so MinIO can be swapped for AWS S3/GCS later without code changes.
  6. Build data export/delete capabilities early — much cheaper than retrofitting for compliance later.
  7. Automate migrations (Flyway), backups, and observability before go-live, not after.

15. Legal, Compliance & Go-Live Readiness

This section turns the compliance note above into an implementation workstream. It is a planning checklist, not a legal opinion or certification. Before production use, counsel and qualified privacy/security professionals must confirm which laws apply, who is responsible for compliance, and whether the proposed controls satisfy the applicable obligations.

15.1 Establish the regulatory scope

Create a written data and jurisdiction inventory before collecting real health information. The applicable obligations depend on where the patient, provider, organization, and infrastructure are located, and on the role MedVault plays in each workflow.

15.2 Assign accountability and obtain approvals

  • Assign an executive owner, product owner, security owner, privacy owner, and incident commander.
  • Document the customer organization's responsibilities separately from MedVault's responsibilities.
  • Identify whether a Data Protection Officer, privacy officer, security officer, or local representative is required.
  • Define the process for legal review of new features, new data types, new countries, and new vendors.
  • Obtain written approval for the privacy notice, consent language where required, terms of service, records policy, and support access policy.
  • Do not use real patient data for development, demonstrations, test fixtures, or screenshots unless specifically approved and protected for that purpose.

15.3 Privacy engineering requirements

  • Collect only the minimum data required for a documented product purpose.
  • Make each processing purpose explicit and document the lawful basis or other required justification with counsel.
  • Separate account identity data, clinical records, audit data, analytics, and support data where practical.
  • Provide clear notices explaining collection, use, sharing, storage locations, retention, rights, and contact channels.
  • Use privacy-preserving defaults: private records, disabled public links, minimal profile visibility, and no sensitive data in URLs or notifications.
  • Complete a privacy impact assessment or equivalent risk assessment before production launch and whenever the processing materially changes.
  • Define whether product analytics, error tracking, email providers, OCR services, AI services, and customer support tools may receive health data. Default to no health data.

15.4 HIPAA and healthcare-contract readiness

Where HIPAA applies, counsel must determine the covered-entity and business-associate relationships and the required contract terms. The implementation should support, at minimum:

  • Business Associate Agreements where required, including permitted uses, safeguards, subcontractors, breach reporting, return or destruction, and audit cooperation.
  • Administrative, physical, and technical safeguard documentation tied to the HIPAA Security Rule and the organization's risk analysis.
  • Individual access, amendment, accounting, and restriction workflows where applicable to the customer's obligations.
  • Minimum-necessary access, unique user identification, emergency access procedures, automatic session controls, and audit review.
  • A documented breach assessment and notification process with named owners and regulatory deadlines verified by counsel.

15.5 GDPR and regional privacy readiness

Where GDPR or similar privacy law applies, counsel should confirm roles, lawful bases, special-category data requirements, international-transfer mechanisms, and the applicable representative or authority obligations. The product should provide:

  • Data-subject request workflows for access, correction, deletion, restriction, portability, and objection when applicable.
  • Identity verification and authorization checks before releasing or changing a person's records.
  • Request tracking with intake date, scope, identity evidence, decisions, exports, exceptions, and completion date.
  • Mechanisms to find all copies, derivatives, indexes, thumbnails, exports, backups, and shared links associated with a record.
  • Documented retention exceptions where deletion is restricted by law, clinical obligations, litigation hold, accounting rules, or customer policy.
  • Transfer assessments and approved safeguards for vendors or infrastructure outside the relevant jurisdiction.

15.6 Security controls required before real data

  • Enforce MFA for administrators and privileged users; require it for all users when the risk assessment supports that decision.
  • Use least privilege, tenant isolation, resource-level authorization, and server-side checks for every read, download, share, update, and delete operation.
  • Encrypt data in transit and at rest, manage keys separately, rotate secrets, and document key recovery and revocation procedures.
  • Keep audit events append-only and tamper-evident, including actor, subject, action, timestamp, result, source, and correlation identifier.
  • Redact health data, tokens, passwords, and encryption material from application logs, traces, crash reports, notifications, and analytics.
  • Scan uploads for malware, validate file type and size, prevent path traversal, and isolate document preview or OCR processing.
  • Apply secure session handling, rate limits, brute-force protection, CSRF protection where applicable, secure headers, and dependency patching.
  • Complete independent penetration testing, remediation tracking, vulnerability scanning, backup restoration testing, and disaster-recovery testing.

15.7 Retention, deletion, and legal hold

Retention must be policy-driven rather than implemented as an arbitrary timeout. For each record category, define the retention owner, minimum and maximum period, deletion trigger, legal hold behavior, backup treatment, and verification evidence.

Record categoryPolicy decisionsTechnical behavior
Clinical documentsRequired retention period, patient request rules, clinical or legal exceptionsVersioned deletion workflow, object deletion, metadata cleanup, and deletion audit event
Account and identity dataWhen inactive accounts and identity evidence may be removedAccount closure workflow with dependency checks and confirmation
Audit recordsRequired duration, immutability, access restrictions, and export processAppend-only storage with restricted administrative access
Backups and replicasExpiration, restore handling, legal holds, and deletion verificationDocumented lifecycle rules and periodic restoration tests

15.8 Vendors, subprocessors, and contracts

  • Maintain a live vendor register for hosting, object storage, email, SMS, OCR, search, monitoring, support, authentication, and payment services.
  • Record each vendor's data access, storage region, subprocessors, security documentation, incident contact, retention behavior, and deletion guarantees.
  • Complete security and privacy due diligence before enabling a vendor with health-data access.
  • Execute required Data Processing Agreements, Business Associate Agreements, confidentiality terms, security addenda, and transfer terms.
  • Provide customer notice and an objection or approval process for material subprocessor changes where required.
  • Ensure contracts address breach notification timing, cooperation, audit rights, return or deletion, business continuity, and termination assistance.

15.9 Incident response and breach readiness

  1. Detect: Alert on suspicious login activity, privilege changes, bulk downloads, unusual sharing, malware, failed authorization, and data exfiltration signals.
  2. Contain: Revoke sessions and tokens, disable affected accounts or links, isolate workloads, preserve evidence, and protect unaffected tenants.
  3. Assess: Determine what data, people, systems, and jurisdictions are affected, when exposure began, and whether the event is reportable.
  4. Notify: Follow approved contractual, regulatory, and customer notification procedures after counsel confirms the content and timing.
  5. Recover: Remove persistence, restore from verified backups, rotate credentials, validate controls, and monitor for recurrence.
  6. Learn: Complete a post-incident review, document corrective actions, assign owners and deadlines, and test the updated response plan.

15.10 Required compliance evidence

Store versioned evidence in a restricted compliance repository. A production approval package should include:

  • Approved data inventory, system and data-flow diagrams, risk assessment, privacy impact assessment, and jurisdiction matrix.
  • Access-control matrix, role reviews, MFA coverage, privileged-access approvals, and sample audit-log reviews.
  • Security architecture, encryption and key-management design, vulnerability reports, penetration-test results, and remediation decisions.
  • Retention schedule, deletion test results, backup restoration results, disaster-recovery results, and legal-hold procedure.
  • Vendor register, security reviews, contracts, subprocessor list, hosting-region confirmation, and transfer assessments.
  • Privacy notices, terms, consent records where applicable, request-handling procedure, incident-response plan, and training records.
  • Release approval signed by product, security, privacy, operations, and legal/compliance owners.

15.12 Go-live decision

Do not enable real patient data until the accountable owners can answer yes to all of the following: the legal role and jurisdictions are confirmed; required contracts and notices are approved; access and tenant isolation are tested; audit, deletion, export, and incident workflows are operational; backups and recovery are verified; vendors are reviewed; staff are trained; and unresolved risks have written acceptance from the authorized decision-maker.

Generated planning document — not a substitute for formal legal/compliance review (HIPAA, GDPR, or local health-data regulations) before handling real patient data in production.
